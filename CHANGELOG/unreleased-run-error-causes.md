- **Breaking:** `RunError::new` refuses `RunErrorKind::Config` the way it already refuses `External` and `App`; construct a configuration failure with `RunError::config(message, error)`, which takes the cause and cannot drop it. Every configuration failure the framework raises now carries a `source()`: a clapfig resolution failure downcasts to `clapfig::ClapfigError`, so a caller can read the offending key and its file position instead of matching on rendered prose. Render and final-write failures gain the same shape through `RunError::render(message, error)` and `RunError::final_write(message, error, OutputKind)`, and the paths that carry the run's own output now use them: a template render or record-array serialization downcasts to `standout::RenderError`, a handler result or artifact receipt that will not serialize downcasts to `serde_json::Error`, and the final-write failures that #564 made inspectable keep their `std::io::Error`. Incremental events are the one framework failure still reported as prose alone: a serialization or template failure raised from `emit` reaches the run as a `Render` error with no `source()`, because `EventSink::record_failure` borrows an `EmitError` it must also return to the handler and `serde_json::Error` cannot be cloned or rebuilt the way the write arm rebuilds its `io::Error`. `RunError::new` still accepts `Render` and `FinalWrite`, which also have framework-composed failures with no underlying error (a command naming a template with no registry configured; an artifact with no destination selected) (closes #572).
