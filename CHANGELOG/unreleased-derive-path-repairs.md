- Make the derive path compose in the combinations the docs lead with (issues #349, #350, #355, #358, #360). `#[derive(Dispatch)]` now registers a variant under its kebab-case name — `ListUnits` becomes `list-units`, the spelling clap's own derive gives the subcommand — and `#[dispatch(name = "...")]` renames one variant; the handler is still looked up under the variant's snake-case name, so `ListUnits` still calls `handlers::list_units`. **This renames every multi-word command a `#[derive(Dispatch)]` app registers**: an app whose clap definition declares `list_units` renames the subcommand or takes `#[dispatch(name = "list_units")]`. A registration that no clap subcommand can reach used to end the run with no output and a `false` return from `App::run`; `run`, `dispatch_from` and `App::verify_command` now check every registered path against the clap `Command` up front and fail with an error naming the unreachable path, plus the clap spelling when the two differ only in `-` versus `_`. A clap subcommand with no registration is untouched: that is partial adoption, and it still hands off as `NoMatch`. The check reads canonical command names: since clap resolves an alias before dispatch sees the command, a handler registered under an alias (`ls` against `Command::new("list").alias("ls")`) is reachable by neither spelling and is reported, and registering `list` is what makes both spellings run it. `#[dispatch(pure, simple)]` and `#[dispatch(pure, handler = ...)]` are rejected at expansion with a message naming both attributes and what each one does, rather than an arity error from inside the expansion, and they are rejected whether written in one `#[dispatch(...)]` or spread over several, since a variant's attributes now merge before anything reads them. A `#[dispatch(name = "...")]` carrying a `.` is rejected too: dispatch splits registration paths on `.`, so such a name registered a nested path no clap subcommand declares.
- Let one `standout` dependency carry the macros (issue #360). `#[handler]`, `Questionnaire` and `QuestionnaireChoices` named `standout_dispatch` and `standout_input` in their expansions, so a crate that depended on `standout` alone — as `docs/crates/input/topics/framework-integration.md` says is enough — failed to resolve them. Each expansion now names whichever crate the consuming crate declared, read from its manifest, and `standout` re-exports `standout-dispatch` as `standout::dispatch` alongside the existing `standout::input`. The generated `name__handler` and `name__expected_args` items carry their own `#[allow(non_snake_case)]` (issue #358), so a consumer under `deny(warnings)` compiles clean without an allow of its own; `standout-fixtures`' `derive_surface` module is that consumer, and it depends on `standout` and nothing else.
- State the `#[handler]` parameter-to-argument rule where the macro is (issue #349). Underscores in a parameter name become hyphens, so `no_legend` reads the argument whose id is `no-legend`. Clap's derive ids an argument by the field name, which is why the two disagreed silently until a `get_flag` panicked; the rustdoc on `#[handler]` and the handler-contract topic now both state the rule and the two ways to meet it. A name that is a Rust keyword goes through the same rule: `#[handler] fn r#move(#[flag] r#type: bool)` generates `move__handler` and reads the argument id `type`, where the macros used to panic mid-expansion on the `r#`.
