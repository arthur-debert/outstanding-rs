- Select the command lexically, before parsing (issue #292, PR #293, ADR-0018). The token in command position is read as a name: if it names a command, that command is what the line means; only a line that names none takes a default command. Under the old parse-first ordering a flat CLI with required root arguments could not have a working `help` word — the requirements fired before anything could decide what the word meant, so an injected `help` subcommand was advertised in help output and could never run. `help` is now installed for CLIs with subcommands and for flat CLIs with no positionals, and behind the new `.help_word(true)` for a flat CLI with positionals, where a bare word is data and only the application knows whether its domain excludes it (`--` is the escape). The integrated dispatch path (`dispatch_from` / `run` / `run_to_string`) answers help on the same terms as `get_matches_from`, which it previously did not: the same install policy for the word, and `--help` / `-h` rendered through standout instead of handed back as clap's own text. A `help --page` request comes back as the new `SuccessKind::PagedHelp` — `run()` honours it by paging, while the capture APIs return the text and leave the decision to the caller. The same lexical scan now also answers *which* command a `--help` request targets, where a separate walk used to skip every token starting with `-` and take the next word: an option's value could be read as a command name (`myapp --output-file-path list --help` rendered `list`'s help instead of the root's), an alias was not resolved (`myapp ls --help`), and the walk strode past the help request itself (`myapp --help list`). A help render that fails — a broken template or theme, which is what a malformed runtime override stylesheet looks like — is now reported as the application bug it is rather than swallowed: it used to fall through each rendering step and surface as "the subcommand or topic '…' wasn't recognized", blaming a line that was fine, and on the dispatch path it now carries `RunErrorKind::Render` and the failure exit status instead of the usage one. **Breaking:** three API changes come with the new ordering. `DefaultCommandContext::matches()` is removed — a decision taken before parsing cannot be handed parse results, which drops flag-conditional default selection; a flag that chooses a command should be a command. `standout-dispatch`'s `has_subcommand` no longer excludes `"help"`, so a selected `help` subcommand now reads as a selected subcommand. `extract_command_path` and `get_deepest_matches` no longer stop at it either, so an application's own `help` command dispatches like any other; the word is special only where standout answers it before dispatch, and such a word never reaches those matches.
