# Split the configuring builder from the executable app

`AppBuilder` configures and nothing else; `build(self)` consumes it and returns `App`, which owns `run`, `dispatch`, `parse`, and their variants. `App` therefore stops being a re-export of the builder and becomes the built thing, and `App::builder()` returns a builder for the first time rather than another name for the same type. Before this, every entry point was a `&self` method on the builder, so `App::builder().command(…)?.run(cmd, args)` compiled and ran — with no templates loaded into the engine and the theme unresolved, which meant named templates were printed as their own names. A type that can be run before it is configured cannot be documented out of the failure; the ordering rule was written down and the code still accepted the wrong order.

Naming the built type something new, leaving `App` on the builder, was rejected: it hands the awkward name to the type users actually hold and leaves `App` permanently denoting an object that cannot do anything. Typestate on a single `App<Configuring | Built>` was rejected for putting a parameter into every signature that mentions an app, and into downstream types that store one, to express a one-way transition that two plain types express for free. The chosen split is close to source-compatible in practice, because the common downstream line already reads `App::builder()…build()?` and then runs the result; what stops compiling is precisely the unconfigured path. Consuming `self` in `build()` has a second effect worth recording: four panic sites in unrelated files — two in the builder, one in its configuration module, one in the command group module — existed only to enforce "the builder is uniquely owned until `build()` finishes" at runtime, and the move makes that invariant structural.
