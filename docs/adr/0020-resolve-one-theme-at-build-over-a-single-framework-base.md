# Resolve one theme at build over a single framework base

`build()` computes one theme — a framework base, being the default theme plus the help vocabulary, the topic vocabulary, and the framework styles, with the application's theme merged over it so the application wins per tag — and every surface renders from that one value. `Theme::merge` already existed with exactly these semantics; the defect was that nothing called it for help. Instead the application's theme was copied into the help configuration wholesale, which made `default_help_theme()` dead code for any application that set a theme at all, so a themed application rendered literal `[about?]` and `[header?]` markup on its own help page, and only on a terminal — pipes stripped the markers, which is how the defect survived release verification. Alongside it sat five separate answers to "the theme when none is set" and four call sites that had to remember to pass the application's theme along. Per-surface resolution was considered and rejected: the isolation it appears to buy is illusory, since the application's theme merges into each surface anyway, and it preserves three resolution rules where one suffices just as the composition-contracts work is about to unify those surfaces. Merging at each point of use was rejected for keeping the scattered definitions and staying forgettable — a new call site that omits the merge silently reintroduces the original defect. Folding the framework styles into the base also settles a second dead switch: `FRAMEWORK_STYLES` was defined and never consumed, so the framework's own list-view template emitted `[standout-muted?]` into user output.

The visible consequence is that an application defining `header` restyles its help headers too. That is intended — one theme means one look — and a surface that later needs its own vocabulary should get namespaced tags rather than a second resolution path.

Unknown tags are then checked in two places, and the split between them is a contract rather than a convenience. A tag whose name is a literal in template source is statically discoverable, and every registered template is validated at `build()` against the resolved theme using the tag-validation primitive `standout-bbparser` already exposes — until now applied only to templates in isolation rather than to the composed template-and-theme artifact — so a literal tag with no style is a setup error naming the template, the tag, and its near matches. Build validation cannot be exhaustive, and claiming otherwise would be false: a template may construct a tag name from a runtime value, which the framework's own list-view template does with `[standout-{{ msg.level }}]`. Such names are unresolvable at build by construction. So the runtime check is the universal net rather than a rare latecomer path: the rendered output is diagnosed on every render, and any tag not in the resolved theme — dynamically constructed, arriving through a hot-reloaded file, or otherwise — renders as its unstyled inner text and emits a warning through the existing channel. Failing the render instead was rejected, because the readiest way to reach it is editing a template during a hot-reload session, and erroring would break the one workflow that lateness exists to serve. This retires the `[tag?]` marker, which documentation described as a visible warning and which in practice leaked template internals to end users. Two consequences follow for the implementation: where build-time exhaustiveness is wanted the tag name must be literal, so the framework's own dynamic message tag is rewritten to its four literal alternatives; and handler data interpolated into output can still contain tag-like text, which this decision does not address — escaping rendered data is a separate question, named here so it is not mistaken for something the build check covers.
