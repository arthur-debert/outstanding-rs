# Split render into TargetProperties and RenderRequest

`standout-render` exposes two public types, not one. **`TargetProperties`** is properties of the destination being rendered to for one invocation — width, stdout color capability, stderr color capability, color-scheme, icon mode, whether stdout is a terminal, whether stderr is a terminal, ambiguous-width policy. Color capability is per stream because stdout and stderr can differ (piped command, TTY warnings): primary rendering consumes stdout facts; warnings and progress consume stderr facts. It is what detection returns, what `TestHarness` injects, and what later color / pager / progress read. **`RenderRequest`** is what to render — data, template, theme, format, plus a `TargetProperties` — and is `render_request`'s only input. `App` after `build()` stays the build-time bundle (ADR-0021): it holds configured fallbacks, not per-invocation resolved mode, theme, or target properties. There is no public `ResolvedConfig`. `RenderContext` stays the borrowed view handed to context providers mid-render; it is not the leaf's entry.

Both types are owned. `TargetProperties` is `Copy` (width, bools, small enums). `RenderRequest` owns what it must and keeps the engine and registry behind the `Rc` the glue already uses. A lifetime on `RenderRequest` was rejected: the artifact path defers render until after the write, so today `Presentation` exists as an owned snapshot of the pipeline; a borrowed request would need that second type again, which is the duplicate this work deletes. Cheap-ness is `Copy` plus `Rc`, not `'a` on the public API.

One struct was rejected: detection happens before data and template exist, so a single type is either legal to `render_request` while half-empty, or forces `detect()` to know about templates. Folding destination properties into `App` was rejected because they are per-invocation and ADR-0021 already made `App` the thing `build()` knows. Reusing `RenderContext` was rejected because that type's job is the provider API, and stuffing detection into it would make every context provider depend on the leaf's entry shape. `RuntimeProperties` was rejected because "runtime" reads as the whole run — including `--output`, which lives on `RenderRequest` — and recreates the god-object. `Capabilities` was rejected because the word already means compile-time Resource operations (ADR-0002 and siblings), because color capability is already a pair of fields on this bundle (stdout and stderr), and because width is a measurement, light/dark a preference, and ambiguous-width an application policy, not things the host "can do." A single `color capability` was rejected: ADR-0022 already showed that a stdout-only fact cannot model stderr warnings on `command | consumer`.
