# Questionnaire Answer Sheets

## Context

`standout-input` already provides composable input sources, validation, terminal-aware prompts, and test responders. Its interactive-flow guidance deliberately leaves each application's wizard state machine and accumulated domain state to the application.

The `standout new-project` bootstrap wizard follows that ownership model. It collects project and command answers interactively, validates them into a private `ProjectSpec`, shows a review, asks for confirmation, and only then publishes a generated project. The shipped wizard is complete, but its questionnaire cannot be rendered for offline editing or answered from a file or piped standard input.

This Spec adds a reusable, documented answer-sheet capability to `standout-input` and proves it through the bootstrap wizard. It preserves the boundary established by the existing wizard ADR: Standout Input owns input collection machinery, while the application owns its questionnaire definition, domain types, branching, review, confirmation, and side effects.

## Problem

Long or repeatable questionnaires are awkward to complete only as a sequence of terminal prompts. Users cannot inspect the whole questionnaire before answering, edit it with ordinary text tools, keep an answer sheet for a repeatable workflow, or prepare answers for an attended or automated run.

Using a general configuration format such as TOML would make the file look executable and implementation-oriented rather than like a questionnaire. Generating application code from submitted text would also put the boundary in the wrong place: file and stdin are merely alternative ways to collect answers, and the wizard must remain the authority that interprets and validates them.

Offline collection also introduces compatibility and validation problems. Display numbers and question wording will change, repeatable groups have variable counts, conditionally applicable fields cannot dynamically appear and disappear in a static document, and a batch submission should report all useful errors rather than failing at the first invalid field.

## Goals

- Add a public, reusable, and documented questionnaire answer-sheet capability to `standout-input`.
- Let applications define static questionnaires containing scalar fields, nested groups, and repeatable groups without transferring ownership of application domain types or flow control to the library.
- Render a prose-first answer sheet that is comfortable to read and edit as text.
- Give every field and group a stable semantic ID while treating question numbers, wording, indentation, and type hints as presentation only.
- Render the minimum number of occurrences for a repeatable group and make adding occurrences a copy-and-edit operation.
- Parse answers from a named file or explicit piped stdin into the same raw answer representation used by interactive collection.
- Use shared field decoders and validators so equivalent interactive and batch answers produce the same application-owned answer and domain models.
- Preserve immediate, one-question-at-a-time feedback for interactive users while accumulating field and whole-form diagnostics for batch users.
- Reject stale or incompatible answer sheets predictably through exact questionnaire identity and semantic-fingerprint matching in the first release.
- Integrate answer-sheet generation and consumption into `standout new-project` without weakening its review, confirmation, validation, or no-partial-write guarantees.

## Non-Goals

- A general configuration-file language or executable configuration format.
- Generating Rust code, templates, or project files directly from raw answer-sheet text.
- Moving `WizardAnswers`, `ProjectSpec`, project generation, or application-specific validation into `standout-input` or exposing `ProjectSpec` publicly.
- A generic wizard state machine, arbitrary imperative branching, resume/checkpoint support, or dynamically changing an already-rendered answer sheet.
- Fuzzy matching, automatic migration, best-effort recovery, or field renaming across incompatible questionnaire definitions in the first release.
- Merging interactive answers with file or stdin answers through a precedence chain.
- Explicitly clearing or suppressing a declared default through a blank answer in the first release.
- Adopting declarative `InputChain` resolution in the projects generated by the bootstrap wizard; that is separate work.

## Proposed Shape

`standout-input` gains a public questionnaire module with a small declarative definition surface and three cooperating capabilities: render a blank answer sheet, collect or parse raw answers, and decode and validate those answers. The module is documented as a reusable library feature rather than as bootstrap-wizard-only support.

An application owns its questionnaire definition. A definition gives the questionnaire a stable identity and describes stable field and group IDs, value kinds, optionality, nesting, repeat bounds, constraints, defaults, and conditional applicability. A definition is static: it can describe which values are applicable given other values, but it does not run arbitrary branches or rewrite a rendered document. The application also owns conversion from validated questionnaire values into its domain model, whole-form rules, its interactive flow, review, confirmation, and all side effects.

### Prose answer-sheet format

The rendered artifact is an answer sheet, not a configuration file. A representative document is:

```text
#! standout-answers 1
#! questionnaire: standout.new-project
#! fingerprint: sha256:7a81c1d8...

1. What is the project name? [project.name] (string)
-> wizard-question-generator

2. Describe the initial command. [command] (section)

2.1 What is the command name? [command.name] (string)
-> generate

3. Describe a command input. [command.inputs] (repeatable section, minimum 1)

3.1 What is its name? [command.inputs.name] (string)
-> definition

3.2 What type of value is it? [command.inputs.value_type] (string, bool, or path)
-> path

3.3 Where can its value come from? [command.inputs.sources] (list)
-> argument

4. Add any notes. [project.notes] (text, optional)
->
This answer may span several lines.
Internal line breaks remain part of the answer.
```

The bracketed token is the stable machine identity. Visible numbers, prose, type hints, whitespace, and indentation are cosmetic and may change without changing answer identity. The schema, not the cosmetic type hint, determines decoding.

A field header is recognized by a bracketed ID together with its following `->` answer marker. The schema must recognize that ID as a field in the current scope. Content on the marker line and subsequent lines belongs to that answer until the next recognized field or group header or end of file. Leading and trailing whitespace around the complete answer is removed, while internal line breaks are preserved.

A group occurrence header is recognized separately: its bracketed ID must name a group allowed in the current schema scope, it does not use an answer marker, and it is followed by a recognized child field or group permitted by that group's definition. Unknown IDs and duplicate or misnested known IDs in header-shaped lines are diagnostics rather than ignored text. Merely writing ordinary prose containing brackets or a known ID inside an answer does not open a field or group; it must satisfy the corresponding header contract, including the following `->` marker for a field and the schema-valid child header for a group.

The renderer pre-fills every declared default. During collection, any blank field resolves to its declared default first. When no default exists, a blank optional field means omission and a blank required field produces a missing-value error. Interactive and batch collection apply this same rule.

A repeatable-group header opens one occurrence, and its child field IDs are scoped to that occurrence. Additional occurrences are expressed by copying the complete rendered group block. A submitted value can therefore be diagnosed as `command.inputs[1].name` while the stable definition ID remains `command.inputs.name`; array indexes belong to an answer instance, not to the definition.

The renderer emits exactly the declared minimum number of repeatable-group blocks. It includes short editing guidance for copying a whole block when more items are wanted. Nested numbering such as `3.2` helps people understand structure but has no parsing or compatibility meaning. Variable item counts are inferred from occurrences of the stable repeatable-group header, never from display numbers or heuristics over question wording.

The metadata preamble is deliberately small and visually separate from the questions. It carries an answer-format version, questionnaire ID, and semantic fingerprint under the unambiguous `fingerprint` key. The first release accepts only the expected answer-format version, exact questionnaire ID, and exact fingerprint. A mismatch produces a diagnostic telling the user to render a fresh answer sheet; it never guesses which old field maps to which new field.

The fingerprint is computed from a canonical, short semantic definition. It includes stable IDs, value kinds, optionality, group structure, repeat bounds, defaults, constraints, conditional-applicability rules, and explicit revisions for application validators whose semantics cannot otherwise be represented. It excludes question wording, help text, display numbers, presentation order, indentation, and styling. It is a compatibility checksum, not an authenticity or tamper-proofing mechanism.

### Collection and validation

Interactive prompts, named answer files, and explicit stdin answer sheets normalize into one raw answer model before application-domain conversion. All paths use the same field decoders and field validators. The application then applies the same whole-form validation and converts a successful result into its private answer and domain types.

Interactive collection keeps its immediate feedback loop: decode or field-validation failures are shown at the current question and the user can answer again without losing earlier valid answers. Batch collection parses the whole document, then accumulates all useful syntax, identity, structure, missing-value, type-conversion, field-validation, and cross-field diagnostics. Diagnostics identify fields by stable ID and, for repeated values, by occurrence path.

Static answer sheets render the superset of declared fields rather than attempting a dynamic conditional flow. A conditionally applicable required field must be answered when active and may remain blank when inactive. Supplying a value for an inactive field is an error; the application does not silently ignore stale or contradictory input. Arbitrary imperative conditional flows remain application-owned and interactive-only.

### Bootstrap-wizard integration

Running `standout new-project` without an answer-sheet option remains the interactive experience. The wizard gains a questionnaire-rendering command that writes the blank answer sheet to stdout by default and can write it to a requested file. Rendering performs no project generation.

```sh
# Render a blank answer sheet to stdout.
standout new-project questions

# Render a blank answer sheet to a file.
standout new-project questions --file answers.txt

# Generate from a named answer sheet.
standout new-project --answers answers.txt

# Generate from an answer sheet on stdin, with attended confirmation.
standout new-project --answers - < answers.txt

# Generate from stdin without prompting for confirmation.
standout new-project --answers - --yes < answers.txt
```

The generation path accepts `--answers FILE` or `--answers -`. A named path reads one complete answer sheet from that file; `-` reads one complete answer sheet from stdin. Selecting either mode replaces interactive question collection rather than merging sources. Parse or validation failures report the accumulated diagnostics and publish no project files.

After successful conversion, every collection mode uses the existing project review and confirmation gate. `--yes` explicitly skips the confirmation prompt for attended or automated runs. Without `--yes`, the wizard shows the review and asks for confirmation through an attended terminal, including when the answer sheet itself came from stdin. If no attended terminal is available, it fails before publishing any files and explains that the user must rerun in a terminal or pass `--yes`.

## User / Agent Stories

1. As a wizard user, I want to print the complete questionnaire before answering, so that I can understand the requested information and prepare it at my own pace.
2. As a wizard user, I want an answer sheet that reads like questions and answers, so that I do not need to understand a configuration language.
3. As a wizard user, I want to edit answers in my preferred editor and submit the file later, so that long and repeated answers are manageable.
4. As an automation author, I want to submit an exact-version answer sheet on stdin with `--yes`, so that an otherwise identical wizard run can be unattended.
5. As an attended stdin user, I want the wizard to review my submitted answers and ask for confirmation on the terminal, so that piping a file does not silently publish a project.
6. As a user with an invalid answer sheet, I want all independent field and whole-form errors reported together with stable paths, so that I can repair the document in one editing pass.
7. As a user editing a repeatable section, I want the minimum valid number of blocks rendered and clear copy-the-block guidance, so that adding another item is predictable.
8. As a user with a stale answer sheet, I want a precise compatibility error instead of guessed field matches, so that changed questionnaire semantics cannot produce an unintended project.
9. As a `standout-input` adopter, I want to reuse rendering, parsing, normalization, and diagnostics while keeping my wizard definition and domain model private, so that the library provides a deep input boundary rather than an application framework.
10. As a bootstrap-wizard maintainer, I want equivalent interactive and answer-sheet submissions to reach the same `WizardAnswers` and `ProjectSpec`, so that collection sources cannot drift in behavior.
11. As a documentation reader, I want a complete public guide and examples for answer sheets, so that the capability can be adopted without reading the bootstrap wizard's implementation.

## Risks And Rabbit Holes

- Treating visible numbers or wording as identity would make harmless copy edits incompatible and would renumber every later answer after an insertion. Only stable bracketed IDs carry identity.
- Treating the answer sheet as TOML, YAML, or another general configuration language would optimize for machine structure at the expense of the intended question-and-answer experience.
- Letting the parser infer renamed or reordered semantics from similar text would make migrations unpredictable. Version 1 rejects an incompatible fingerprint and asks for a fresh sheet.
- Putting application types or `ProjectSpec` into the public library would couple a general input capability to one generator. The library stops at validated questionnaire values and diagnostics.
- Letting each adapter decode independently would create different accepted values and error messages. Interactive, file, and stdin collection must share decoding and validation.
- Reporting only the first batch error would force repeated edit-run cycles. Batch diagnostics must accumulate without allowing invalid partial state to reach project generation.
- Silently discarding populated inactive fields would hide stale or contradictory intent. They are validation errors.
- Adding a full migration engine, arbitrary conditional language, or general form-rendering system would delay the useful file/stdin path and create contracts not yet justified by real consumers.
- Header-like bracketed IDs inside free-form answers require an unambiguous parser contract and focused tests; cosmetic freedom must not make document boundaries guesswork.
- Consuming stdin for the answer sheet and then trying to confirm on the same stream would either fail or accidentally treat answer content as confirmation. Confirmation must use an attended-terminal seam independent of the answer stream.

## Cross-Cutting Concerns

- **Compatibility:** The answer-format version and exact semantic fingerprint are explicit. Wording-only and numbering-only changes do not invalidate a document. Semantic changes do, and version 1 provides regeneration rather than migration.
- **Security and privacy:** Answer sheets may contain application-sensitive information. Diagnostics should identify fields without echoing full submitted values by default, and public documentation must warn users to protect answer files appropriately. The fingerprint does not authenticate content.
- **Failure safety:** Parsing, validation, review rejection, missing attended confirmation, and cancellation all occur before project publication. Existing staging-and-rename publication guarantees remain in force.
- **Terminal behavior:** File and stdin collection do not imply consent. Confirmation uses a terminal-capable prompt unless `--yes` is explicit; lack of a terminal is an actionable error, not implicit approval.
- **Observability:** User-facing diagnostics use stable IDs and occurrence paths so an edited answer sheet can be repaired directly. Compatibility errors report expected and received questionnaire metadata without dumping answers.
- **Documentation and release:** The public `standout-input` documentation must define the format, application/library ownership boundary, definition and validation model, repeated-group editing, compatibility rules, security considerations, and complete examples. Bootstrap-wizard documentation must cover rendering, file/stdin submission, confirmation, and automation.
- **Performance:** Answer sheets are ordinary wizard-sized text documents. Parsing should be single-pass or similarly bounded and must not require loading generated projects or invoking code generation before validation succeeds.

## Testing / Verification

All four seams are mandatory:

1. **Pure answer-sheet engine:** Test questionnaire definition validation, deterministic rendering, metadata and fingerprint behavior, scalar and multiline parsing, cosmetic wording and numbering changes, stable IDs, nested and repeatable groups, minimum-count rendering, copied repeated blocks, whitespace rules, unknown/duplicate/missing or misplaced IDs, conditional applicability, type conversion, and accumulated diagnostics.
2. **Collection adapters:** Test interactive, named-file, and explicit-stdin collection through their real abstractions, including terminal detection, EOF/cancellation, malformed documents, stdin consumed before confirmation, and `--yes` behavior. Tests must not require a real terminal.
3. **Equivalence:** Supply semantically identical answers through interactive prompts and answer sheets and assert equality at both the application-owned raw/typed answer boundary and the resulting private domain model. Include representative nested, repeated, multiline, optional, and conditional cases.
4. **Real CLI flows:** Exercise questionnaire generation to stdout and a file, `--answers FILE`, `--answers -`, review and confirmation, `--yes`, stale fingerprints, accumulated form errors, inactive populated fields, user rejection, missing attended terminals, and success/failure publication behavior. Every failure before confirmation must prove that no destination is written.

Public documentation examples and doctests are part of verification. Existing prompt-responder and `TestHarness` seams should be reused so interactive and end-to-end behavior remain deterministic in CI.

## Workstream Hints

- Begin with a narrow, documented answer-sheet definition/render/parse path in `standout-input` that can round-trip one scalar questionnaire end to end.
- Extend that path coherently to nested and repeatable groups, semantic fingerprinting, shared decoding, conditional validation, and accumulated diagnostics.
- Adopt the public capability in the bootstrap wizard, preserving its private domain conversion, review, confirmation, and atomic publication boundary.
- Complete the feature with public library guidance, bootstrap-wizard workflow documentation, equivalence tests, and real CLI acceptance proof.

These are planning hints only; issue decomposition happens after the Spec and ADR are reviewed and merged.

## Out Of Scope

- Implementing the feature in this planning change.
- Creating an epic or workstream issues before the Spec and ADR are reviewed and merged.
- Automatically migrating or rewriting old answer sheets.
- Supporting arbitrary runtime question insertion, loops, jumps, or side-effect-dependent branches in a static answer sheet.
- Combining partial answers from several files, stdin, command-line arguments, environment variables, or interactive prompts.
- Encrypting answer sheets or treating their fingerprint as a signature.
- Changing the generated project's input-source wiring or replacing its typed Clap helpers with `InputChain` declarations.
- Turning the bootstrap wizard's private project schema into a public compatibility contract.
